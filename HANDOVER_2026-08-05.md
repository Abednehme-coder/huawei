## 1. Val→test gap — cross-check done, conclusion revised

**What happened**: `CSV-01-12.zip` (the official per-flow label CSV this
doc was waiting on) finished downloading via a third path (see §3 for the
saga). Extracted `Syn.csv` (637MB, 1,582,681 flow rows, the SYN-flood
attack-type export for `01-12-2018`) and ran the actual cross-check
(`scripts/diagnose_test_gap_infer.py` → predictions dump →
`scripts/diagnose_test_gap_crossref.py` → the comparison itself).

**What was confirmed**:
- 97% concentration replicates: of 2,136 test false positives (continued
  checkpoint, current full test-set numbers — not the 3,024 quoted this
  morning, which was against different checkpoint state), 2,071 (97.0%)
  sit in `SAT-01-12-2018_0617`/`_0619`.
- Timezone resolved definitively: `window_features_real.csv`'s `t0_unix`
  is raw pcap epoch UTC (unambiguous). `Syn.csv`'s `Timestamp` is
  `America/Halifax` local (AST, UTC-4 on this date) — self-consistent,
  its flows cluster in `13:30:30`–`13:34:27` local, matching
  `scripts/cic_ddos2019_syn_windows.json`'s documented `13:29`–`13:34`
  schedule almost exactly.

**What changed the conclusion**: `Syn.csv` only covers that narrow
~4-minute window — it's CICFlowMeter's per-attack-type export, not a
full-day capture. Of the 2,071 flagged false positives:
- Only 192 fall within 60s of that window; **1,879 range as early as
  17:05:18 UTC, up to 24 minutes before the attack starts** — a period
  `Syn.csv` has zero records for, so no verdict is possible from it either
  way.
- Direct cross-reference (±2s tolerance): **86 have a matching official
  `Syn`-labeled flow** (genuine confirmed mislabels). **0 match
  `BENIGN`-only. 1,985 have no official record at all.**
- For those 1,985 un-verifiable ones: feature stats show them measurably
  busier than genuine true-negatives in the same stem (`syn_ratio` 0.080
  vs. 0.044, `n_packets` 302.6 vs. 122.4) — but a visual contact sheet (8
  sampled false positives vs. confirmed-ddos vs. confirmed-normal, same
  stem) shows they look like sparse background traffic, **not** the
  bright horizontal-line SYN-flood signature the confirmed-ddos tiles
  clearly show. Likely genuinely unusual-but-normal traffic, not
  disguised attack traffic.

**Corrected metric** (relabeling only the 86 confirmed mislabels, from the
continued checkpoint's actual confusion matrix TP=822/FN=144/FP=2136/TN=7287,
n=10389):

| | raw test | corrected (86 relabeled) |
|---|---|---|
| accuracy | 0.7805 | 0.7889 |
| ddos precision | 0.278 | 0.307 |
| ddos recall | 0.851 | 0.863 |
| **ddos f1** | **0.419** | **0.453** |

**For the paper**: report this as a real, partially-explained
generalization gap — "4% of test false positives on the held-out attack
day are confirmed label-boundary artifacts; correcting them moves
`ddos_f1` from 0.419 to 0.453; the remainder appears to be genuine
model imprecision on busier-than-typical normal traffic, not a labeling
problem" — rather than the much rosier "boundary artifact, true
performance is 0.932" framing from this morning. This is a more modest
but far more defensible claim.

## 1b. If there's a power shutdown right now — where to resume

This machine has lost power mid-run multiple times before (see
`WORK_LOG.md` 2026-08-04 entries — 4 power losses during the flowpic
training alone), so here's exactly what to do for each of the two things
currently running:

**Bytedump training (§2 below)** — `train_resnext.py` has **no
optimizer/LR-schedule checkpointing**, only weight loading via `--ckpt`
(same limitation noted for the flowpic run's continuation script,
`scripts/train_resnext_flowpic_v1_continue.sh`). A power loss mid-run
does NOT corrupt anything already saved to disk, but does NOT let you
resume the *schedule* either — you restart with a fresh cosine schedule
from the best saved weights, same pattern as that continuation script.
1. Check what's on disk: `ls -la model/per_second_0p3_validated_v1/` —
   look for `resnext50_32x4d_best.ckpt` (the best-val-`f1_ddos` checkpoint,
   updated every time val improves — as of 22:34 EEST this is epoch 2's
   weights) and the rolling per-epoch checkpoints
   (`resnext50_32x4d-N_2399.ckpt`, last 5 kept, `N`=epoch).
2. If `resnext50_32x4d_best.ckpt` exists, resume from it into a **new**
   output dir (don't overwrite what's there):
   ```bash
   cd /home/abed/Documents/huawei
   OUTPUT_DIR=model/per_second_0p3_validated_v1_recovered \
     nohup bash scripts/train_resnext_per_second_0p3_validated_v1.sh \
     --ckpt model/per_second_0p3_validated_v1/resnext50_32x4d_best.ckpt \
     --strict-load \
     > model/per_second_0p3_validated_v1_recovered_train.log 2>&1 &
   disown
   ```
   (creates `OUTPUT_DIR` itself via the script's `mkdir -p`.) If training
   had barely progressed (still in the first few epochs, which is where
   this recipe is known to oscillate — see §2), it's equally reasonable to
   just restart the original command fresh instead of resuming from a
   possibly-mediocre early checkpoint — judgment call, not a hard rule.
3. Re-launch the crash-watching monitor (see `TO_RUN.sh` for the tail
   command) and re-verify against the log for `Traceback`/`CUDA
   error`/`OOM` before assuming it's healthy.

**CSV-03-11.zip pull (§3 below)** — **no resume support at all**, the
