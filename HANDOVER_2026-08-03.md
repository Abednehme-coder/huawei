### Superseded: single-stream rsync was way too slow
The plain `rsync --partial --append-verify` approach above technically

asked if there was a better way. There was:

### Current approach: parallel byte-range fetch (much faster)
Measured directly (not assumed): single SSH stream ~0.07 MB/s, **4-way
parallel ~0.43 MB/s (6x), 8-way ~0.59-0.72 MB/s (8-10x)**. 16-way barely
improved further and started hitting sshd connection-accept limits
(`kex_exchange_identification: Connection closed by remote host`), so
**8-way is the sweet spot**. This works by reading distinct byte ranges of
the (never-unzipped, just-read) source file on the server via `dd
skip=/count=` with `iflag=skip_bytes,count_bytes`, streamed over SSH, and
written into the correspondingly-seeked offset of the local file via `dd
oflag=seek_bytes conv=notrunc`. **No unzip, no disk writes on the server at
all** — this is pure read-only network streaming, safe to run there.

Script (kept in `dataset/PCAPs_raw/parallel_fetch_0250.sh`, gitignored like
the rest of `dataset/` but persists on this machine's disk, not `/tmp`):
splits the remaining byte range into 266 chunks of 32MiB, runs 8 concurrent
workers (`xargs -P 8`) each pulling one chunk at a time with unlimited
per-chunk retry (900s timeout per attempt) until the byte count actually
matches. **Resumable across restarts**: on each (re)launch it re-reads its
own log (`dataset/PCAPs_raw/parallel_transfer_0250.log`, which lives in the
repo tree, not `/tmp`, so it survives a reboot) for previous `OK start=N`
lines and skips those chunks — a restart loses at most whatever chunks were
*in flight* at the moment of the restart, not the whole run.

**Debugging note, don't repeat this mistake**: the first version of this
script had a real bug, not just slowness — it parsed the wrong field out of
`dd`'s stderr summary. `dd` prints `"N+M records in"` first (M = number of
*short* reads, ~always nonzero and largely irrelevant over a network pipe)
and the actual byte count on a separate `"NNNN bytes (...) copied"` line.
The original parse grabbed the leading number off the *first* line, which
is the full-block record count — effectively always `0` for network-piped
data — so every chunk was logged as a 0-byte failure and endlessly retried
**even though the underlying data transfer was working fine**. Fixed by
matching `^[0-9]+ bytes` instead. Confirmed via an isolated manual test
before trusting the fix (a 4MB test chunk genuinely transferred in 15.4s,
~0.27MB/s, and the "0 records" line was just a red herring).

Also hit and resolved mid-session: an **earlier** version of the
single-stream `resume_transfer_0250.sh` wrapper (§ below, now obsolete) had
a `while true` retry loop that kept silently resurrecting plain `rsync`
processes every time one was killed, which briefly raced against the new
parallel fetcher writing to the *same* destination file. Fully swept with
`pkill -9 -f "91.99.170.219"` before restarting cleanly, and — because
concurrent uncoordinated writers had touched the byte range from
571,473,920 up to ~1.6GB — that whole range was discarded (truncated back
to the last independently-verified-safe boundary, 571,473,920 bytes) and
re-fetched from scratch under the fixed script, rather than trusting
whatever was sitting there. If you ever see two transfer mechanisms running
at once again, kill both immediately and re-verify from the last known-good
boundary rather than assuming partial data is fine.

## 3. Recovering after a local machine restart

The parallel fetcher is resumable (see above — it reads its own log and
skips already-`OK` chunks), but only if you **re-run the actual script**,
not blindly re-run some other command. From the repo root:

```bash
cd ~/Documents/huawei
bash dataset/PCAPs_raw/parallel_fetch_0250.sh 571473920
```

- `571473920` is the `START_FROM` argument — the last independently-verified
  safe boundary from this session. Keep using this same value on every
  relaunch; the script's own resume logic (skipping already-OK chunks from
  the log) handles the rest.
- Do **not** delete `dataset/PCAPs_raw/PCAP-01-12_0250-0499.zip` or
  `dataset/PCAPs_raw/parallel_transfer_0250.log` before doing this — the log
  is what makes the resume skip-list work, and the destination file is
  pre-truncated (sparse) to the full 9,474,338,816-byte target size; deleting
  either throws away real progress.
- If you ever need to check whether it's still running:
  ```bash
  ps aux | grep "[p]arallel_fetch_0250\|[f]etch_chunk"
  ```
  If nothing shows up and the log doesn't end with `ALL CHUNKS DONE`, just
  re-run the command above — safe to run repeatedly, it won't duplicate
  already-completed work (beyond a few seconds re-scanning the log).
- Progress / status from scratch:
  ```bash
  du -B1 dataset/PCAPs_raw/PCAP-01-12_0250-0499.zip | cut -f1   # actual bytes on disk so far
  stat -c%s dataset/PCAPs_raw/PCAP-01-12_0250-0499.zip          # should read 9474338816 (sparse target size, not progress)
  tail -30 dataset/PCAPs_raw/parallel_transfer_0250.log
  grep -c ' OK ' dataset/PCAPs_raw/parallel_transfer_0250.log   # completed chunks (out of 266)
  ```
- The server side (`91.99.170.219`) is a separate machine, **unaffected** by
  a local restart — nothing to redo there. It's only ever being *read* by
  this approach (via `dd`), never written to — safe by construction, unlike
  the abandoned unzip-on-server approach.
- Once **all 266 chunks show `OK`** (or the log ends with `ALL CHUNKS DONE`),
  verify integrity before using the file:
  `unzip -t dataset/PCAPs_raw/PCAP-01-12_0250-0499.zip` should say "No
  errors detected" — then proceed to §6 step 2 (run
  `generate_validated_images_batch.sh` **locally**, never on the server).
- Any Claude-harness "background bash" watcher IDs from this session
  (`b8keujimy`, `bdbqljnsz`, `bgn60bbtn`, `brk67r27t`, `bldmcrud3`) are
  **session-scoped and won't exist in a new session** — don't try to look
  them up, use the commands above instead.
