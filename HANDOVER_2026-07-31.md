## 2. Part one: local code (Day 1–3 of the plan)

Implemented and tested, zero PCAP/server dependency, exactly as scheduled:

- `scripts/pcap_to_images.py::parse_ipv4_header` — additive 5-tuple/TCP-flags
  parser (src/dst IP, ports, proto, full flags byte, IP total len). Mirrors
  `is_tcp_syn`'s Ethernet(+VLAN)/IPv4 detection; `is_tcp_syn` itself untouched.
- `scripts/extract_window_features.py` (+ `extract_window_features_batch.sh`)
  — single-pass per-window feature CSV: packet/byte counts, SYN/ACK/FIN/RST
  ratios, unique src/dst IP counts + Shannon entropy, packet-size and
  inter-arrival-time mean/std (Welford's algorithm, no scipy needed).
  `in_schedule` + `heuristic_label` carried only for old-vs-new comparison.
- `scripts/cluster_validate_labels.py` — the actual scientific core: KMeans
  (k=2) per capture day on standardized flow features, cross-tabulated
  against the CIC schedule label (agree→keep, disagree→drop as ambiguous).
  GMM/DBSCAN run as reported-only robustness cross-checks (Adjusted Rand
  Index vs. KMeans), never affecting the resolved label. Hard fallback: if a
  day's silhouette < 0.15, that day auto-switches to `schedule_priority`
  (keep 100% of schedule labels, drop nothing) — enforced in code, not a
  judgment call under deadline pressure.
  Added `scikit-learn` + `pandas` to `.venv`/`requirements.txt`
  (`reports/pip_freeze_2026-07-30.txt`).
- `scripts/pcap_to_images.py::run_time_window_mode` — additive
  `--label-source {schedule_syn,external}` + `--external-labels PATH`.
  Default (`schedule_syn`) behavior confirmed byte-for-byte unchanged via a
  regression test. Matching env plumbing (`LABEL_SOURCE`,
  `EXTERNAL_LABELS_JSON`) added to `convert_pcaps_to_images.sh`;
  `process_zips_in_batches.sh` deliberately untouched.
- **27/27 tests pass** (`  .venv/bin/pytest tests/`), 16 new across
  `test_extract_window_features.py`, `test_cluster_validate_labels.py`,
  `test_pcap_to_images_external_labels.py`.

**Side finding, not fixed, flagged in `WORK_LOG.md`**: `run_time_window_mode`'s
output filename truncates `t0_unix` to whole seconds. For sub-1s windows
(the primary model uses 0.3s), consecutive buckets can round to the same
integer second; if two also share the same `syn_count` (plausible for
normal traffic with repeated `syn_count=0`), one image silently overwrites
another in the same class directory. Predates this session, not introduced
by it. Could mean the current primary dataset has fewer effectively-unique
"normal" images than reported file counts imply. Not acted on — would need
dataset regeneration, outside this session's scope.
